# 架构与数据流：批次汇总、条件批量程序与幂等上报

> 本文是**实现口径的落点**：代码注释说「为什么这么定」，本文说「定成什么」。
> 口径只定义一次 —— 本文与 `src/push/batch.rs` 的注释是同一份口径的两处投影，
> 改一处必须改另一处。

## 1. 主路径

```
科室专项上报表 (xlsx / csv)
        │
        ▼
 regval validate ──► 本机校验库 (.regval/state.db)
        │                rows / issues / batch_summaries
        ▼
 结果契约 JSON (schema_version = regval.contract/1.0.0)
        │
        ▼
 Excel / WPS 宏 ──► 原表新增 5 列（校验结论 / 问题类型 / 问题说明 / 疑似重复项 / 上报状态）
        │
        ▼  （经办人勾选确认）
 regval push ──► 幂等键 → 条件批量提交计划 → 条件批量执行 → 网关 POST → 回执
        │
        ▼
 行级状态（已上报 / 被退回 / 待重试） ──► 批次汇总 ──► regval status / 未上报名单
```

## 1.1 三入口同构：契约是唯一的接缝

科室可能只碰得到三条入口里的一条，所以**判定口径只能有一处**：

| 入口 | 宿主 | 写回载体 |
|------|------|----------|
| Excel 加载宏 | 桌面 Excel（VBA） | `Range.Value2` 批量写回 5 个新列 |
| WPS JSA 宏 | 装了 WPS 的报送机（JSA） | 同上（对象模型不同，判定口径相同） |
| CSV 直跑 | 禁宏的专网报送机 | 人工按列粘贴（契约 JSON 是人工可读的表格） |

三条入口的共同点是：**它们都不做判定**。口径规则、问题数、疑似重复、状态条那句
成品话，都在引擎里算好，装进**带 `schema_version` 的结果契约 JSON**；宏只负责
「取契约 → 写回载体」。

```
                   ┌──────────────── 引擎（判定只有这一处）────────────────┐
                   │  口径规则引擎 · 重复检测漏斗 · 状态条句子（statusbar） │
                   └───────────────────────┬──────────────────────────────┘
                                           │ 结果契约 JSON（schema_version）
              ┌────────────────────────────┼────────────────────────────┐
              ▼                            ▼                            ▼
      Excel 宏（VBA）                 WPS 宏（JSA）                CSV 直跑
      读契约 → 写回 5 列             读契约 → 写回 5 列            读契约 → 人工粘贴
```

由此产生三条硬约束：

1. **版本闸门**：契约 `schema_version` 与宏常量对不上 → **中止写回**，
   三条入口行为一致（都报 `CONTRACT_VERSION_MISMATCH` + 同一句中文）。
   宁可什么都不写，也不写一半。
2. **宏不自行统计**：状态条那句「已校验 N 行 · M 项口径问题 · K 项疑似重复待确认」
   由引擎算好放进 `summary.status_line`，宏原样显示 —— 表里与终端里必须是一句话。
   （宏里出现 `Rows.Count -` 这类自行统计的写法，测试会红。）
3. **常量只有一处出处**：WPS 宏的契约常量、视觉 token、提示文案由引擎**注入**
   （`regval macro` 装配 `macro/wps/regval.js`），不手抄；改了 token 或文案，
   重新装配一次，Excel 侧（`regval tokens --vba` / `regval messages --vba`）与
   WPS 侧同时变。

一致性由 `tests/three_entry_consistency_test.rs` 盯着：同一份样例走 CSV 直跑与
表格入口，两份契约的业务内容逐字段比对；WPS 侧用宿主替身（`tests/wps_harness/run.js`）
真跑一遍宏，核对写回的 5 列与契约逐字段一致、原表一格没动；版本不符时三条入口
都拒绝写回并报同一个错误码。

> **边界**：WPS 侧的宿主是替身（宏逻辑与引擎真跑，宿主不是真 WPS）；Excel 侧本轮
> 环境没有 Excel，VBA 走同源核对（两侧常量、读的契约键、按钮、版本闸门、错误码
> 逐项比对），不是执行。真机首次导入后仍需人工点一次确认渲染。

## 1.2 读表层：判定只有一处，丢行留痕

读表是三入口的共同起点，所以**判定口径也只有一处**
（`src/ingest/quality.rs` 的 `classify`，CSV 与 Excel 共用）：

| 行的判定 | 判据 | 处置 |
|---------|------|------|
| 有效行 | 必填业务列（指标编号 / 指标名称 / 科室代码 / 报告期 / 业务主键）至少一格有值 | 参与校验 |
| 空行 | 所有格都是空或纯空白 | 不参与校验，**计数留痕** |
| 重复表头 | 与表头逐格一致（归一后） | 不参与校验，**计数留痕** |
| 分隔线 | 非空格全是横线/等号一类的分隔字符 | 不参与校验，**计数留痕** |
| 无效行 | 有内容但必填业务列一格没值（备注行、合计行标题） | 不参与校验，**计数留痕** |

**留痕**是硬要求：跳过的行号与原因进契约 `ingest.skipped_detail`，计数进
`summary.source_rows` / `blank_rows` / `invalid_rows` / `skipped_rows` /
`skipped_note`，终端照实打一行。表里 8 行、校验了 5 行，另外 3 行是什么、
为什么不算 —— 一眼看得见，不靠回原表数一遍。

**CSV 入口的容错**（`src/ingest/csv.rs`）：

| 脏数据 | 处理 |
|--------|------|
| GBK 编码 | 逐行解码；整表记 `gbk`，与 UTF-8 混着记 `mixed` |
| UTF-16 | 明说不支持（`INPUT_UNREADABLE`），不做乱码替换 |
| 某行既不是 UTF-8 也不是 GBK | 报错并点名**第几行**，不产出契约文件 |
| 全角逗号分隔 | 表头里只有全角逗号时，引号外的全角逗号归一成半角 |
| 列名带空格 | 表头归一后照常映射 |

> **为什么 CSV 要自己按物理行切一遍**：csv crate 会跳过整行空白的行。
> 空行要是在 CSV 这边被吞了，后面的行号就整体错位 —— 「第 7 行」指的是不同的行，
> 报给科室就没意义了。所以 `split_physical_lines` / `align_rows` 把空行按原位补回，
> 让两条入口的行数与行号完全一致。

一致性由 `tests/csv_fallback_test.rs` 盯着（脏数据读得对、丢行计数对、
错误码对、CSV 与 xlsx 两路读入后契约业务内容逐字段相同）。

## 2. 批次汇总：口径与事务

批次汇总回答一个问题：**这批数据整体算不算数**。它不是一个报表系统，
就四项口径 + 几个批次计数，供 `regval status` 与未上报名单共用。

### 2.1 汇总口径（四项，固定）

| 口径 | 定义 | 数据出处 |
|---|---|---|
| 已上报行数 | 网关已受理的行数（本次受理 + 幂等命中） | `submissions.status = 已上报` |
| 被退回行数 | 网关退回（4xx）的行数 | `submissions.status = 被退回` |
| 待重试行数 | 可重试失败（5xx / 超时 / 连不上）的行数 | `submissions.status = 待重试` |
| 问题项数 | 该批次问题条数（口径问题 + 上报退回问题） | `issues` 表 |

另附批次计数（计划步数、尝试数、受理数、幂等命中数、未发出数、回执待核对数、
未执行数）与已上报行的填报值 / 分子 / 分母合计，供经办人核对这一批的总量。

**口径的读法**：四项都从**本机库的权威状态**算，不从执行器的自述算 ——
执行器说「我受理了 3 行」与库里「3 行的状态是已上报」对不上时，以库里的为准。
「未发出 / 回执待人工核对 / 未执行」既没报上去、也不在等网关恢复，
**不计入**这四项 —— 混进来会让「还差多少」算不清。

**状态取值只有一处**：`src/push/status.rs`（「已上报」「被退回」「待重试」…）。
库表、汇总口径、待办清单、导出产物都引它，不各写一份。

### 2.2 批次状态

| 取值 | 含义 |
|---|---|
| 已校验 | 校验完成，还没上报 |
| 上报完成 | 上报整批跑完（无回滚） |
| 部分完成 | 批次没整批跑完（有失败或未执行），但没触发回滚（续跑场景） |
| 批末回滚 | 批末条件回滚已触发，汇总回到批前值 |

### 2.3 一次事务

批次计数、汇总值与批次状态在**一个事务**里写进本机库：

1. 写/更新 `batch_summaries` 的**快照**行（一个批次一行，永远是最新那版）；
2. 追加一行 `batch_summary_history`（**append-only**，`(batch_ref, revision)` 唯一）。

第 2 步撞唯一索引（同一版汇总被写第二次 —— 重放）→ **整次事务回滚**，
第 1 步写进去的快照一起撤销，快照回到批前值。

> **为什么必须一次事务**：半截的汇总比没有汇总更坏。
> 「已上报 3 行」配「被退回 0 行」看着像一批干净的账，实际只写进去一半 ——
> 经办人会照着它去催科室。

修订号由快照表当前修订号 +1 得出，**不接受调用方指定** ——
否则重放能覆盖历史。历史表只追加不修改：更正以新记录表达。

### 2.4 批末回滚：回滚账，不回滚事实

上报是条件批量程序：第 i 步只在第 i-1 步成功后执行。
第 k 步失败 → 第 k+1..N 步不执行 → 批末条件回滚触发。

回滚触发时：

| 东西 | 回不回滚 | 为什么 |
|---|---|---|
| 批次计数、汇总值、批次状态 | **回滚**（回到批前值） | 整批没跑完就不落账；下次重跑还是从零算起，不会把半批当成一批 |
| 行级回执（`receipts`） | **不回滚** | 网关已经受理了那一行 —— 那是**已经发生的外部事实**，本机库改不掉。回滚它等于假装没上报过，而网关那边真撤不回来 |
| 行级状态（`submissions.status`） | **不回滚** | 同上：这一行确实已经报上去了 |

## 3. 条件批量程序

```
待推送行（按 row_uid 排序，可复现）
   │
   ├─ 幂等命中的行 ──► 不进程序，进「已跳过」清单
   ├─ 跨表取值一致的行 ──► 只编一行
   └─ 跨表取值不同的行 ──► 一行都不编，进「待人工判定」（不二选一）
   │
   ▼
Program = [ Step{cond: None}, Step{cond: Ok{step:0}}, Step{cond: Ok{step:1}}, … ]
   │
   ▼ 执行（逐步）
 第 i 步成功？──否──► 第 i+1..N 步不执行（记「未执行」，不是静默跳过）
   │是
   ▼
 批末条件：末步没成功 → 回滚批次汇总（行级回执保留）
```

失败分类（决定这一行要不要重试）：

| 分类 | 触发 | 行状态 |
|---|---|---|
| 可重试 | 5xx / 超时 / 连不上 | 待重试 |
| 不可重试 | 4xx 退回（带错误码与字段名） | 被退回 |
| 不可重试 | 200 但回执缺字段或受理时间非法 | 回执待人工核对 |
| 不可重试 | 本行数据不合格（请求根本没发出去） | 未发出（数据不合格） |
| 幂等命中 | 台账里已有这一行的回执 | 幂等命中（已上报，不重复推送） |

**失败不静默**：每一步失败都写进行状态（含机器可读错误码）与审计链，
不吞异常、不改写成成功。上报接上去的必须是网关的裁决，
不是本地的时间，也不是执行器的乐观假设。

## 3.1 上报发送链（`src/push/send.rs`）

上面几层各自做扎实一件事；发送链把它们接成一条：

```
编译（program.rs）
   │
   ▼
恢复台账（retry.rs restore_ledger）── 从本机库读回回执与行级状态
   │                                   └─ 续跑点据此算：已有回执的行不重复推送
   ▼
过写闸门（gate.rs）── 没确认过的行一个字节都不发
   │
   ▼
逐步执行（executor.rs + retry.rs）── 第 i 步只在第 i-1 步成功后执行
   │                                   └─ 5xx / 超时退避重试，4xx 不重试
   ▼
落库（receipt.rs + batch.rs）── 回执 / 提交记录 / 行状态 / 审计链 / 批次汇总
```

**执行与落库分两段**：写闸门要**读**状态库，落库要**写**状态库 —— 同一个
`Repo` 上不能同时持有一个可变借用和一个不可变借用。执行段拿 `&Repo`，
落库段拿 `&mut Repo`，两段之间只靠 `SendOutcome`（逐行裁决 + 行级推进结果）传递。

**跨进程续跑**：进程重启后新进程的台账是空的。把本机库里的回执与行级状态
读回台账（`restore_ledger`），续跑点才算得出来 —— 不读回来，已上报的行会被再推一遍。
本机库那一层还有一道保险：**载荷摘要没变且已报上去**的行在编译阶段就判幂等命中，
根本不进上报程序。

**「没报上去」不等于「重复提交」**：载荷摘要没变时，判成重复提交（跳过）的只有
两种 —— 已上报、已被网关退回（退回是数据问题，改完数据摘要就变了，会自动走订正重报）。
待重试 / 未发出 / 未执行 / 回执待人工核对这四种都**没报上去**，一律回到上报程序
（沿用同一修订号与同一幂等键）。判成跳过就等于把这一行永远钉在没报上去的状态里，
经办人也催不动。

## 4. 幂等与回执

- **幂等键** = sha256(机构代码｜报告期｜指标编号｜科室代码｜业务主键)；
  **载荷摘要** = sha256(固定字段顺序 + 浮点定形的规范化 JSON)。
- 同一个幂等键下摘要变了 = **订正**（修订号 +1，业务键不变）；
  摘要没变 = **重复提交**（不重复推送）。
- **幂等键 ↔ 回执 ID 一一对应**：`receipts` 上 `(idempotency_key, revision)` 与
  `receipt_id` 两个唯一索引兜住。撞了报 `RECEIPT_CONFLICT`，已有回执不覆盖。
- **回执是状态推进的唯一依据**：不由模型、不由本地时间推进。
  只有受理（200）才有回执；退回没有回执号，待重试更没有。

## 4.1 回执台账（`src/report/receipt.rs`）

留档与第三方核对用的产物。**一次提交一条**，按「幂等键 + 修订号」计：

```
submissions（一次提交 = 一个 (幂等键, 修订号)）
    │
    ├─ LEFT JOIN receipts（按 (幂等键, 修订号)）→ 回执号 / 受理时间 / 网关状态
    ├─ 行状态（row_states，按行键）               → 行状态
    ├─ 上报退回问题（R-PUSH-GATEWAY，按行键）      → 网关说明（退回原话）
    └─ 行级口径版本（rows.rule_version，按行键）   → 这批结论按哪套口径算的
                        │
                        ▼
        回执台账（CSV：列名与顺序固定；JSON：多一段 cross_check）
```

- **订正重报出两条**：同一业务行改了数据再报，幂等键不变、修订号 +1、
  载荷摘要变、网关给**另一个**回执号 —— 按「幂等键 + 修订号」记一条，两边才对得上。
- **`cross_check` 段**给第三方核对要的结论：一一对应成立没有、已上报却无回执、
  有回执却无提交记录、上报状态与行状态对不对得上、逐条冲突明细。
- **核对不通过时退出码非 0**：台账仍然写出来（写出来是为了让人照着查），
  但不当作干净台账归档 —— 错误码 `RECEIPT_LEDGER_MISMATCH`。
- **只读**：本模块不写任何表、不推进任何状态。行状态只由网关回执驱动。

## 5. 本机校验库的表

| 表 | 放什么 | 谁写 |
|---|---|---|
| `rows` | 落到本机库的行列级数据（带来源命名空间，多来源互不覆盖） | 校验引擎 |
| `issues` | 口径问题与上报退回问题 | 规则执行器 / 回执落库 |
| `confirmations` | 人工确认与撤销记录 | 确认流 |
| `audit_log` | 审计链（append-only） | 全部写操作 |
| `submissions` | 上报提交（幂等键 + 载荷摘要 + 修订号 + 当前状态） | 上报执行器 |
| `receipts` | 上报网关回执 | 回执解析 |
| `batch_summaries` | 批次汇总**快照**（一批一行） | 批次汇总落库层 |
| `batch_summary_history` | 批次汇总**历史**（append-only） | 批次汇总落库层 |
| `row_states` | **行级状态机**状态（状态 + 行级版本号 + 数据摘要） | 状态机（唯一写入方） |
| `run_summaries` | 每次命令的运行摘要 | 引擎 |
| `dept_directory_cache` | HIS 科室主数据目录缓存（含数据时间） | 科室目录客户端 |
| `model_call_audit` | 模型调用元数据与降级标记 | 模型审计层 |

结构版本由 `schema_migrations` 记录，按序迁移、幂等；
版本高于引擎则拒绝打开（不降级、不重建空库）。

## 5.1 审计链与状态库恢复（`src/state/audit.rs` / `src/db/journal.rs` / `src/db/recover.rs`）

**审计链（`audit_log`，append-only）**

| 事件 | 谁写 | 说明 |
|---|---|---|
| `confirm` / `revoke` / `merge` | 确认流 | 人工确认、撤销、疑似重复逐条勾选合并 |
| `push.accepted` / `push.rejected` / `push.retryable` / `push.idempotent_hit` | 回执落库 | 这一批推了什么；说明里带**幂等键 + 修订号 + 回执 ID** |
| `push_blocked` | 写闸门 | 未确认就推，闸门拦下（一个字节都没发） |
| `recover.restored` | 状态库恢复 | 恢复动作本身也留痕 |

读侧：`regval audit --row <行键>` 回放这一行的完整轨迹（谁确认的 → 什么时候推的 → 拿到哪个回执）；
`regval audit --batch <批次>` 回放这一批推了什么；
`regval audit --idempotency` 核对幂等键 ↔ 回执 ID 的一一对应（孤儿回执 / 缺回执 / 回执号重复）。

**恢复日志（`<状态库>.journal`，append-only 边车文件）**

状态库是单文件 SQLite，坏了就什么都读不出来 —— 包括「这一行已经报给网关了」这条外部事实。
所以上报侧的关键事实另写一份到库旁边：每行一条 JSON（`receipt` / `submission` / `batch_commit`）。
打开方式是 `append(true)`：写不进已有内容，只能往后接；崩溃时最后一行可能是半截的，读的时候跳过并计数。

**恢复（`regval recover`）**

1. 库完好 → 「无需恢复」，一个字节都不动；
2. 库坏了 → 恢复源有两个：**恢复日志**（通常还活着）+ **原库残留**（局部损坏时别的表可能还读得出）；
3. 恢复产物写 `<状态库>.recovered`，**原库不动**；`--apply` 才换位（原库挪成 `.corrupt-N` 备份，不删）；
4. 恢复报告说清**恢复到哪一批**（最后一条批次提交标记）与**丢了什么**（校验结论、口径问题、行状态、半截批次）。

回执**一律全恢复** —— 回执是网关已经受理的事实，哪怕那一批没跑到最后；
少恢复一条，重跑时那一行就会被再推一遍。

## 6. 行级状态机（`src/state/machine.rs`）

### 6.1 六个状态与合法迁移表

```
待校验 ──校验通过──▶ 校验通过 ──人工确认──▶ 待确认 ──网关受理──▶ 已上报
   ▲                    │                      │
   │                    │                      ├──网关退回──▶ 被退回 ──修正后──▶ 待确认
   │                    │                      │
   └──复校验不通过──────┘                      └──可重试失败──▶ 待重试 ──重试成功──▶ 已上报
```

迁移表是**白名单**（`LEGAL_TRANSITIONS`）：表外的一律拒绝并报
`INVALID_STATE_TRANSITION`，**状态一个字节都不动**（连版本号都不动）。
典型被拒的迁移：`待校验 → 已上报`（没过校验就上报）、
`校验通过 → 已上报`（跳过人工确认）、`已上报 → 被退回`（受理过的那一版不会变退回）、
`已上报 → 校验通过`（已上报的行不得被普通校验改回）。

三个上报后状态的字面量直接引用 `src/push/status.rs` —— 同一串字两处各写一份，
迟早会出现「库里写着已上报、状态机却当没报过」。

### 6.2 单一入口与行级乐观锁

- 所有状态推进都走 `machine::advance(conn, &StateChange)`；
  `row_states` 表的 `INSERT` / `UPDATE` 语句**只出现在这个模块里**
  （`tests/row_state_machine_test.rs` 里有静态判据守着这条）。
- 推进时用「读到的版本号」做条件更新（`UPDATE ... WHERE version = ?`）——
  抢写的那一方拿到 `ROW_STATE_CONFLICT`，不会把别人的结果盖掉。
  调用方也可以带 `expected_version`：版本对不上直接报错，不写。
- 状态推进记 `updated_at` / `updated_by` / `reason`（谁在何时把哪一行推到哪一步）。

### 6.3 两条业务规矩（普通校验不越权）

| 情形 | 行为 | 为什么 |
|---|---|---|
| **已上报的行** | 普通校验**不改**它的状态；内容变了只记一条提示 | 网关已经受理过，校验改不回「待校验」，否则经办人以为还没报上去 |
| **被退回的行** | 数据摘要变了（= 修正过）→ 回到**待确认**（需重新确认）；摘要没变 → 保持被退回 | 修正过才能重新确认；没改就别急着重报 |
| **复校验不通过** | `校验通过` / `待确认` → 退回 `待校验` | 旧的确认作废 |

数据摘要 = sha256(指标编号｜科室代码｜报告期｜业务主键｜分子｜分母｜填报值｜单位)，
不含行号与时间 —— 换个人重报同一份表，摘要不变。

## 7. 不变量

- **幂等键**：同一业务行两次计算必须相同；改填报值不改幂等键，只改载荷摘要与修订号。
- **重放防护**：同一版批次汇总写第二次 → 撞 `(batch_ref, revision)` 唯一索引 → 整次事务回滚。
- **一次事务**：批次计数、汇总值、批次状态要么全落、要么全不落。
- **状态校验**：行级状态只由回执推进；模型与本地时钟都不推进状态列。
- **状态迁移白名单**：不在合法迁移表里的状态推进一律拒绝并报错；状态不被静默改写。
- **单一写入口**：`row_states` 表只有 `src/state/machine.rs` 能写。
- **乐观锁**：并发推进同一行时，后写者被拒（`ROW_STATE_CONFLICT`），不覆盖先写者。
- **失败不静默**：每一步失败都有机器可读错误码与审计条目。
- **回滚范围**：只回滚批次汇总；行级回执与行级状态不回滚。
- **审计链只追加**：`audit_log` 只有 INSERT，写错了再追加一条更正；写语句只在 `src/state/audit.rs`。
- **恢复不覆盖原库**：状态库损坏时恢复产物写 `<状态库>.recovered`，原库一个字节不动；
  `--apply` 换位时原库挪成 `.corrupt-N` 备份（不删）。
- **判定只有一处**：行是不是「有效行」由 `src/ingest/quality.rs` 一处判定，
  CSV 与 Excel 共用 —— 同一张表从哪条入口进去，跳过了几行、行号对不对得上都一样。
- **台账只读**：`src/report/receipt.rs` 不写任何表、不推进任何状态；
  台账里的行状态与回执号都是从库里读出来的事实。
- **核对不通过不归档**：回执台账交叉核对不通过时退出码非 0
  （`RECEIPT_LEDGER_MISMATCH`）—— 台账仍写出来供逐条查，但不当作干净台账归档。
- **不静默丢行**：空行与完全无效行不参与校验，但必须计数、必须留痕
  （行号 + 原因进契约 `ingest` 段，终端照实打一行）。
- **解不出来就报错**：某一行既不是 UTF-8 也不是 GBK → 报错并点名第几行，
  不拿替换字符糊过去（糊过去中文会变乱码，后面的名称匹配会给出错误提示）。
- **已上报的不重推**：进程重启后先从本机库恢复台账，载荷摘要没变且已报上去的行
  在编译阶段就判幂等命中，根本不进上报程序；续跑只推剩下的行。
- **没报上去的不跳过**：待重试 / 未发出 / 未执行 / 回执待人工核对这四种状态
  一律回到上报程序（沿用同一修订号与幂等键）—— 判成跳过就等于把这一行
  永远钉在没报上去的状态里。
- **写闸门在发请求之前**：没确认过的行**一个字节都不往网关发**，
  拦下时该行留在原状态、审计链留一条 `push_blocked`。
